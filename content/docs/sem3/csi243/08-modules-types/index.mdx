## Chapter 8: Modules and Custom Types

Everything so far has lived in one file and used the types Haskell supplies. This chapter is about organising a program and extending its vocabulary.

Both halves answer the same question — **how do I make a program say what it means?** Modules give structure a name; custom types give data a name.

## `type` or `data`?

The distinction that matters most in this chapter:

| | `type` | `data` |
|---|---|---|
| Creates | A new **name** for an existing type | A genuinely **new type** |
| Interchangeable with the original? | Yes | No |
| Can be recursive? | No | Yes |
| Use it for | Readability | Enforced separation, or a new concept |

If mixing two things would be a real bug, you need `data`. If you only want the signature to read better, `type` is enough.

## Chapter outcomes

- State why splitting a program into modules helps, and name a module correctly.
- Apply the one-module-per-file convention and match the filename.
- Restrict a module's interface with an export list.
- Use all five import forms and resolve a name clash.
- Name the main standard library modules and what each provides.
- Declare type synonyms, including parameterised ones, and explain their limits.
- Declare custom types with `data`, carry values in constructors, and pattern match on them.
- Use `deriving` to obtain `Show`, `Eq`, and `Ord`.
- Define a recursive type and write functions over it with one equation per constructor.
