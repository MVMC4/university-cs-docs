## Chapter 9: Polymorphism and Type Classes

You have been reading signatures like `length :: [a] -> Int` and `div :: Integral a => a -> a -> a` since Chapter 2, with the general parts glossed over. This chapter explains them properly.

Two ideas, and the second solves a problem created by the first:

- **Parametric polymorphism** lets one function work for many types, using a type variable.
- **Type classes** let a type variable carry a requirement, so the function can actually do something with its values.

## The trade-off to carry forward

| Signature | Works on | The function may |
|---|---|---|
| `[Int] -> Int` | Only `Int` | Anything `Int` supports |
| `Num a => [a] -> a` | Any numeric type | Only what `Num` provides |
| `[a] -> Int` | Any type at all | Nothing to the elements |

More constraints means fewer types but more capability; fewer constraints means more types but less capability. **The right signature is the most general one that still permits what the function needs.**

## Chapter outcomes

- Distinguish concrete types from type variables, and read a polymorphic signature.
- Explain what a fully general type variable forbids, and why.
- Apply the type inference rule to check an application by hand.
- Read and write class constraints before the fat arrow.
- Diagnose a "No instance for" error and add the right constraint.
- Name what each standard class provides and which operation needs it.
- Use `fromIntegral` and the rounding functions to move between numeric types.
- Replace `error` with `Maybe` so that failure is visible and recoverable.
- Write your own `Show`, `Eq`, and `Ord` instances, and know when to derive instead.
