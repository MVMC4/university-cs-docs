## 1. Data Types & Variables

Java is a **strongly typed** language, meaning every variable must be declared with a specific data type. This catches errors at compile-time rather than runtime.

### Primitive Data Types
These are the most basic data types built into Java. They hold simple values and are stored in the **Stack** memory for fast access.

<SafeImage 
  src="/images/sem3/csi247/01-java-foundations/primitive-types-chart.png" 
  alt="Java Primitive Data Types" 
  caption="Figure 2: The 8 primitive types with their sizes and ranges"
  className="w-full max-w-4xl mx-auto"
/>

| Type | Size | Range | Default | Example |
| :--- | :--- | :--- | :--- | :--- |
| `byte` | 1 byte | -128 to 127 | 0 | `byte b = 100;` |
| `short` | 2 bytes | -32,768 to 32,767 | 0 | `short s = 30000;` |
| `int` | 4 bytes | ±2 billion | 0 | `int i = 100000;` |
| `long` | 8 bytes | ±9 quintillion | 0L | `long l = 100000L;` |
| `float` | 4 bytes | 6-7 decimal digits | 0.0f | `float f = 5.75f;` |
| `double`| 8 bytes | 15 decimal digits | 0.0d | `double d = 19.99;` |
| `boolean`| 1 bit | true/false | false | `boolean b = true;` |
| `char` | 2 bytes | Unicode character | '\u0000' | `char c = 'A';` |

### Reference Data Types
These refer to objects and arrays. They are stored in the **Heap** memory, and the variable holds a *reference* (memory address) to the actual data.

<SafeImage 
  src="/images/sem3/csi247/01-java-foundations/stack-vs-heap.png" 
  alt="Stack vs Heap Memory" 
  caption="Figure 3: Primitives on Stack, Objects on Heap"

/>

```java
// Reference types examples
String name = "Alice";           // String object
int[] numbers = {1, 2, 3};       // Array object
Scanner sc = new Scanner(System.in); // Scanner object
```

> **Important**: Strings are **NOT** primitives! They're immutable objects.

### Type Casting
Converting one data type to another.

**Widening (Implicit)** - Automatic, safe:
```java
int myInt = 9;
double myDouble = myInt; // 9.0 - no data loss
```

**Narrowing (Explicit)** - Manual, may lose data:
```java
double myDouble = 9.78;
int myInt = (int) myDouble; // 9 - decimal truncated!
```

## 2. Control Flow Statements

Control flow statements dictate the order in which your code is executed.

### Conditional Statements

#### `if`, `else if`, `else`
Used to execute blocks of code based on boolean conditions.

```java
int score = 85;

if (score >= 90) {
    System.out.println("Grade: A");
} else if (score >= 80) {
    System.out.println("Grade: B"); // Executes
} else if (score >= 70) {
    System.out.println("Grade: C");
} else {
    System.out.println("Grade: F");
}
```

<SafeImage 
  src="/images/sem3/csi247/01-java-foundations/if-else-flowchart.png" 
  alt="If-Else Flowchart" 
  caption="Figure 5: Decision tree for grade calculation"
  className="w-full max-w-2xl mx-auto"
/>

#### `switch` Statement
An alternative to long `if-else if` chains.

```java
String day = "WEDNESDAY";

switch (day) {
    case "MONDAY":
        System.out.println("Start of work week");
        break;
    case "WEDNESDAY":
        System.out.println("Midweek!"); // Executes
        break;
    case "FRIDAY":
        System.out.println("Weekend soon");
        break;
    default:
        System.out.println("Another day");
}
```

> **Note**: Without `break`, execution "falls through" to the next case!

### Loops

<SafeImage 
  src="/images/sem3/csi247/01-java-foundations/loop-types-diagram.png" 
  alt="Java Loop Types Comparison" 
  caption="Figure 6: When to use each loop type"
  className="w-full max-w-4xl mx-auto"
/>

1. **`for` Loop** - Known iterations:
```java
for (int i = 0; i < 5; i++) {
    System.out.println("Iteration: " + i);
}
```

2. **`while` Loop** - Condition-based:
```java
int count = 0;
while (count < 3) {
    System.out.println("Count: " + count);
    count++;
}
```

3. **`do-while` Loop** - Executes at least once:
```java
int i = 0;
do {
    System.out.println(i); // Prints 0
    i++;
} while (i < 0); // Condition false, but already ran once
```

4. **Enhanced `for-each` Loop** - Arrays/Collections:
```java
String[] fruits = {"Apple", "Banana", "Cherry"};
for (String fruit : fruits) {
    System.out.println(fruit);
}
```

## 3. Arrays

An array is a fixed-size, contiguous block of memory storing multiple values of the **same type**.

### 1D Arrays

<SafeImage 
  src="/images/sem3/csi247/01-java-foundations/array-memory-layout.png" 
  alt="Array Memory Layout" 
  caption="Figure 7: Contiguous memory allocation with index access"
  className="w-full max-w-3xl mx-auto"
/>

```java
// Declaration and Initialization
int[] numbers = new int[5];        // [0, 0, 0, 0, 0]
int[] primes = {2, 3, 5, 7, 11};   // Shorthand

// Accessing and Modifying
primes[0] = 13;                    // [13, 3, 5, 7, 11]
System.out.println(primes.length); // 5

// Traversing
for (int i = 0; i < primes.length; i++) {
    System.out.println(primes[i]);
}
```

### 2D Arrays (Matrices)

```java
// Create a 3x3 matrix
int[][] matrix = {
    {1, 2, 3},
    {4, 5, 6},
    {7, 8, 9}
};

// Access element at row 1, column 2 (value = 6)
int value = matrix[1][2];
```

<SafeImage 
  src="/images/sem3/csi247/01-java-foundations/2d-array-grid.png" 
  alt="2D Array Visualization"

/>

```java
// Traversing 2D array
for (int row = 0; row < matrix.length; row++) {
    for (int col = 0; col < matrix[row].length; col++) {
        System.out.print(matrix[row][col] + " ");
    }
    System.out.println();
}
```

## 4. User-Defined Classes & Objects

Java is Object-Oriented. **Classes** are blueprints; **Objects** are instances.

### Anatomy of a Class

<SafeImage

  caption="Figure 9: Fields, constructors, and methods"
  className="w-full max-w-3xl mx-auto"
/>

```java
    // 1. Fields (State)

    private int year;

    // 2. Constructor (Initialization)

```

## 5. The Four Pillars of OOP: Architectural Mechanics


Object-Oriented Programming (OOP) is a structural paradigm designed to manage software complexity. 

### 1. Encapsulation: State Protection and Interface Contracts

Encapsulation is the bundling of data (state) and methods (behavior) into a single unit while restricting direct access to internal components. Its primary architectural objective is to enforce class invariants and prevent external state corruption.

#### Access Modifiers and Visibility
Java enforces encapsulation through a four-tier visibility model. Understanding these boundaries is critical for API design.

| Modifier | Class | Package | Subclass | Global | Architectural Use Case |
| :--- | :---: | :---: | :---: | :---: | :--- |
| `private` | Yes | No | No | No | Internal state, sensitive data, implementation details. |
| *default* | Yes | Yes | No | No | Package-private utilities, internal helper classes. |
| `protected` | Yes | Yes | Yes | No | Methods intended for overriding by subclasses. |
| `public` | Yes | Yes | Yes | Yes | The public API contract. |

#### Accessors, Mutators, and Invariant Enforcement
Accessors (getters) and mutators (setters) are not mere syntactic boilerplate; they are validation gates. By routing all state mutations through mutators, a class can enforce invariants and hide its internal data representation from external modules.

```java
public class BankAccount {
    // Hide the data (The Fortress)
    private double balance; 

    // The Setter/Behavior (The Contract & Validation)
    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Deposit must be positive.");
        }
        this.balance += amount;
    }
}
```

<Callout type="warn" title="The Hazard of Public State:">
If a class exposes public mutable fields (e.g., `public double balance`), any external module can corrupt the state (e.g., `account.balance = -5000;`). Encapsulation forces all state transitions through controlled methods, ensuring the object remains in a mathematically valid state.
</Callout>

#### Class-Level State: The `static` Keyword
While encapsulation typically applies to instance state, the `static` keyword designates class-level state.
*   **Static Variables**: Shared across all instances in the JVM Method Area (e.g., tracking the total number of instantiated objects).
*   **Static Methods**: Utility functions that operate without instance context (e.g., `Math.max()`). They cannot access instance variables or utilize the `this` reference.

### 2. Inheritance: Hierarchical Classification and Coupling

Inheritance establishes an "IS-A" relationship, allowing a subclass to inherit the state and behavior of a superclass. It facilitates polymorphic design but introduces tight coupling between classes.

#### Constructor Chaining and `super`
When a subclass is instantiated, Java must initialize the superclass state first. This is achieved via constructor chaining using the `super()` keyword, which must be the first executable statement in the subclass constructor.

```java
public class Vehicle {
    protected String make;
    
    public Vehicle(String make) {
        this.make = make;
        System.out.println("Vehicle constructor called");
    }
}

public class Car extends Vehicle {
    private int numDoors;
    
    public Car(String make, int numDoors) {
        super(make); // CRITICAL: Must be the first line!
        this.numDoors = numDoors;
        System.out.println("Car constructor called");
    }
}
```

**Execution Sequence:**
1. Execution begins when `new Car("Toyota", 4)` is called.
2. The `super(make)` call pauses the `Car` constructor and delegates initialization to the `Vehicle` constructor.
3. The `Vehicle` constructor executes and initializes `make`.
4. Control unwinds back to `Car`, which initializes `numDoors`.

<Callout type="info" title="Architectural Trade-off: Composition over Inheritance">
Inheritance creates a "Fragile Base Class" problem: modifying the superclass can inadvertently break all subclasses. Use inheritance strictly when a true "IS-A" relationship exists. If the goal is merely code reuse or a "HAS-A" relationship, use **Composition** (instantiating the dependency as a private field) to maintain loose coupling.
</Callout>

### 3. Polymorphism: Dynamic Method Dispatch

Polymorphism allows objects of different concrete classes to be treated as objects of a common superclass. The exact method execution is determined at runtime via **Dynamic Method Dispatch**, utilizing the JVM's Virtual Method Table (vtable).

#### Compile-Time vs. Run-Time Polymorphism
1.  **Method Overloading (Compile-Time)**: Multiple methods with the same name but different parameter signatures. The compiler resolves the call based on the static type of the arguments.
2.  **Method Overriding (Run-Time)**: A subclass provides a specific implementation of a superclass method. The JVM resolves the call at runtime based on the actual object in memory (the dynamic type).

#### Polymorphic Collections and Upcasting
Polymorphism enables the creation of heterogeneous collections governed by a unified interface.

```java
// Upcasting: Treating a specific type as a general type (Implicit and safe)
List<PaymentMethod> checkoutCart = new ArrayList<>();

// The list accepts concrete implementations
checkoutCart.add(new CreditCard());
checkoutCart.add(new CryptoWallet());

// Dynamic dispatch: The JVM invokes the correct overridden method at runtime
for (PaymentMethod pm : checkoutCart) {
    pm.pay(100.0); 
}
```
<Callout type="warn" title="Type Casting and Safety">
**Upcasting** (e.g., `PaymentMethod pm = new CreditCard()`) is implicit and always safe. **Downcasting** (e.g., `CreditCard cc = (CreditCard) pm`) is explicit and risky; if the dynamic type does not match the cast, the JVM throws a `ClassCastException`. Always use the `instanceof` operator (or pattern matching in modern Java) to verify the dynamic type before downcasting.
</Callout>

### 4. Abstraction: Hiding Implementation Complexity

Abstraction separates the logical properties of an object (the "what") from its implementation details (the "how"). In Java, this is enforced through Abstract Classes and Interfaces.

#### Abstract Classes vs. Interfaces
An **Abstract Class** cannot be instantiated. It serves as a foundational blueprint, capable of holding both abstract methods (which subclasses *must* implement) and concrete methods (which provide shared default behavior). It can also maintain instance state.

An **Interface** defines a strict contract of behavior. It cannot hold instance state (only `public static final` constants). A class can implement multiple interfaces, solving the multiple-inheritance ambiguity problem inherent in class-based inheritance.

| Feature | Abstract Class | Interface |
| :--- | :--- | :--- |
| **Relationship** | IS-A (Core identity) | CAN-DO / ACTS-AS (Behavioral capability) |
| **State** | Can maintain instance variables | No instance state (only constants) |
| **Constructors** | Yes (invoked by subclasses) | No |
| **Inheritance** | Single inheritance only | Multiple implementation |
| **Access Modifiers**| Any (private, protected, public) | Methods are implicitly public |
| **Design Intent** | Share core code and identity among closely related classes. | Define a capability across unrelated classes. |

#### Design Principle: Program to an Interface
To maximize flexibility and testability, declare variables and method parameters using interface types rather than concrete implementations.

```java
// Rigid: Tied to a specific implementation
ArrayList<String> list = new ArrayList<>();

// Flexible: Tied to an abstraction
List<String> list = new ArrayList<>();
```

By relying on the `List` abstraction, the underlying implementation can be swapped (e.g., to `LinkedList`) without modifying the dependent code. This makes the system pluggable and highly testable (e.g., swapping a real Database for a Mock Database during unit testing).

## 7. Generics

Type-safe code that works with different object types.

### Why Generics?

**Without Generics** (Unsafe):
```java
List list = new ArrayList();
list.add("Hello");
String s = (String) list.get(0); // Risky cast!
```

**With Generics** (Safe):
```java
List<String> list = new ArrayList<>();
list.add("Hello");
String s = list.get(0); // No cast needed!
```

### Generic Classes

```java
public class Box<T> {
    private T item;

    public void setItem(T item) {
        this.item = item;
    }

    public T getItem() {
        return item;
    }
}

Box<Integer> intBox = new Box<>();
intBox.setItem(10);
```

### Bounded Type Parameters

```java
// T must extend Number
public <T extends Number> void printValue(T num) {
    System.out.println(num.doubleValue());
}
```

### Wildcards

1. **`? extends Number`** - Read-only (upper bound)
2. **`? super Integer`** - Write-only (lower bound)  
3. **`?`** - Any type (unbounded)

## 8. Memory Management: Stack vs. Heap

<SafeImage 
  src="/images/sem3/csi247/01-java-foundations/stack-heap-detailed.png" 
  alt="Stack and Heap Memory" 
  caption="Figure 17: Complete memory model with references and objects"
  className="w-full max-w-4xl mx-auto"
/>

### Stack Memory
- **Stores**: Primitives + object references
- **Speed**: Very fast (LIFO)
- **Lifetime**: Method scope
- **Size**: Limited (~1MB per thread)

### Heap Memory
- **Stores**: Actual objects and arrays
- **Speed**: Slower than stack
- **Lifetime**: Until no references exist
- **Management**: Garbage Collector (GC)

```java
public void example() {
    int x = 10;              // Stack: x = 10
    Car myCar;               // Stack: myCar (null reference)
    myCar = new Car();       // Heap: Car object created
                             // Stack: myCar → points to Heap
}                            // Stack cleared, Heap object 
                             // eligible for GC
```

> **Garbage Collection**: When no references point to a Heap object, the GC automatically deletes it.
