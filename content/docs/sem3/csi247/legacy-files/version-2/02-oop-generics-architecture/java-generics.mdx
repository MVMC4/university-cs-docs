## 2.2 Java Generics & Type Erasure

Generics provide compile-time type safety, eliminating the need for explicit casting. However, to maintain backward compatibility with pre-Java 5 code, the JVM implements generics via *type erasure*.

<HighlightCard
  variant="neutral"
  title="Definition 2.2.1: Type Erasure"
  description="The process by which the Java compiler removes all type parameters, replacing them with their bounds or Object."
>

- `<T>` (unbounded) is erased to `Object`.
- `<T extends Number>` is erased to `Number`.
- The compiler inserts explicit casts where necessary to preserve type safety.
- **Consequence:** At runtime, a `List<String>` and a `List<Integer>` are the exact same class (`List`). You cannot use `instanceof` with generic types.

</HighlightCard>

<HighlightCard
  variant="neutral"
  title="Definition 2.2.2: The Generic Array Restriction & Workaround"
  description="Why `new T[]` is illegal and the standard workaround used in ArrayList and HashMap."
>

Arrays in Java are **reified** (they know their component type at runtime and enforce it via `ArrayStoreException`). Generics are **erased** (they do not exist at runtime).

If `new T[]` were allowed, the JVM would not know the actual runtime type to enforce array safety. Therefore, the compiler forbids generic array creation to prevent heap pollution.

**The Standard Workaround:**
When implementing data structures like `ArrayList` or `HashMap` from scratch, you must create an `Object` array and cast it. This requires suppressing the unchecked cast warning.

```java
public class MyArrayList<T> {
    private static final int DEFAULT_CAPACITY = 10;

    // THE WORKAROUND: Cast an Object array to T[]
    @SuppressWarnings("unchecked")
    private T[] elements = (T[]) new Object[DEFAULT_CAPACITY];

    private int size = 0;

    public void add(T item) {
        if (size == elements.length) {
            resize();
        }
        elements[size++] = item;
    }

    private void resize() {
        @SuppressWarnings("unchecked")
        T[] newArray = (T[]) new Object[elements.length * 2];
        System.arraycopy(elements, 0, newArray, 0, size);
        elements = newArray;
    }
}
```
*Note: This is 100% type-safe because the array is `private` and never exposed to the client. The compiler warning is safely suppressed.*

</HighlightCard>

<HighlightCard
  variant="neutral"
  title="Why This Matters for Data Structures"
  description="Connecting Type Erasure and Arrays to real-world Java Collections."
>

- **The Generic Array Workaround:** This exact `@SuppressWarnings("unchecked") T[] arr = (T[]) new Object[capacity];` cast is the foundational boilerplate for `ArrayList`, `HashMap`, and `ArrayDeque`. It allows these core data structures to leverage the $O(1)$ cache locality and memory efficiency of primitive arrays while exposing a 100% type-safe generic API to the client.

</HighlightCard>

<HighlightCard
  variant="neutral"
  title="Definition 2.2.3: PECS (Producer Extends, Consumer Super)"
  description="The rule for using bounded wildcards in method signatures to ensure type safety and flexibility."
>

- **`<? extends T>` (Producer):** Use when the method only *reads* from the collection. It guarantees the elements are at least of type `T`.
- **`<? super T>` (Consumer):** Use when the method only *writes* to the collection. It guarantees the collection can accept at least objects of type `T`.

</HighlightCard>

<StepByStep>
  <StepByStepTitle>Why PECS is Mandatory: The Compilation Error</StepByStepTitle>

  <Step number={1}>
    <StepTitle>The Scenario</StepTitle>
    Suppose we want to write a method that adds numbers to a list. We might naively use `? extends Number`.
    ```java
    public void addNumbers(List<? extends Number> list) {
        list.add(10); // COMPILER ERROR!
    }
    ```
  </Step>

  <Step number={2}>
    <StepTitle>Why it Fails</StepTitle>
    The compiler only knows that `list` contains *some* unknown subtype of `Number`. It could be a `List<Double>`, `List<Float>`, or `List<Short>`.
    Because the compiler cannot guarantee that adding an `Integer` (10) is type-safe for that specific unknown subtype, it **forbids the addition entirely**.
  </Step>

  <Step number={3}>
    <StepTitle>The Correct Way: Consumer Super</StepTitle>
    If we want to *write* (add) elements to a collection, we must use `? super T`.
    ```java
    public <T> void addAll(List<? super T> dest, List<T> src) {
        for (T item : src) {
            dest.add(item); // Compiles successfully!
        }
    }
    ```
    Here, `dest` is guaranteed to be a list of `T` or any *supertype* of `T` (e.g., `List<Object>`). Therefore, adding an object of type `T` is always 100% type-safe.
  </Step>
</StepByStep>

<HighlightCard
  variant="neutral"
  title="Why This Matters for Data Structures"
  description="Connecting PECS to the Java Collections Framework."
>

- **The `Collections` Framework:** The standard library relies heavily on PECS. For example, `Collections.copy(List<? super T> dest, List<? extends T> src)` reads from `src` (Producer) and writes to `dest` (Consumer). Without bounded wildcards, you wouldn't be able to copy a `List<Integer>` into a `List<Number>`, severely limiting the reusability of generic data structure algorithms.

</HighlightCard>

<HighlightCard
  variant="neutral"
  title="Definition 2.2.4: Static Nested Classes & The this$0 Memory Leak"
  description="Why inner classes in data structures MUST be declared static."
>

In Java, a non-static inner class holds an implicit, hidden reference (named `this$0` by the compiler) to the instance of the outer class that created it. 

**Why This Matters for Data Structures:**
We use `private static class Node<T>` in `LinkedList`, `BST`, and `HashMap` specifically to avoid the 8-byte `this$0` memory leak per node. 
- If `Node` were non-static, every single node would carry an extra 8-byte pointer back to the `LinkedList` object. 
- For a list of 1,000,000 nodes, this wastes **8MB of memory**. 
- Worse, if a single `Node` is leaked (e.g., returned to a client), it holds a reference to the entire `LinkedList`, preventing the Garbage Collector from reclaiming the entire data structure even if the main reference is lost.

</HighlightCard>
