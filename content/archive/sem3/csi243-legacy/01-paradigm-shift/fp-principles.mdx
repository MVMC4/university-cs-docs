## 1.2 Core Functional Programming Principles

Functional Programming relies on several foundational principles that distinguish it from imperative paradigms, ensuring modularity, maintainability, and mathematical rigor.

<Card>

### Definition 1.2.1 (Core FP Concepts)

- **Modularity:** Breaking down a program into smaller, independent, and interchangeable components that can be reasoned about in isolation.
- **Immutability:** Once a data structure is created, it cannot be changed. Operations produce new data structures, eliminating bugs related to shared mutable state.
- **Side Effects:** Any observable interaction with the outside world (e.g., modifying global state, I/O). FP strives to isolate and minimise side effects.
- **First-Class Functions:** Functions are treated as "first-class citizens"; they can be assigned to variables, passed as arguments, and returned from other functions.
- **Higher-Order Functions:** Functions that take other functions as arguments or return functions as results (e.g., `map`, `filter`).
- **Function Composition:** Combining two or more functions to produce a new function, where the output of one becomes the input of the next (e.g., `f . g`).

</Card>

<HighlightCard
  variant="neutral"
  title="Definition 1.2.2: Pure vs. Impure Functions"
  description="The strict mathematical criteria for function purity in Functional Programming."
>

A function is **pure** if and only if:
1. **Deterministic:** For the same inputs, it always produces the exact same output.
2. **No Side Effects:** It performs no observable interactions with the outside world and does not mutate external state.

If a function violates either condition, it is **impure**.

</HighlightCard>

<StepByStep>
  <StepByStepTitle>Example: Imperative (Impure) vs. Functional (Pure) Implementation</StepByStepTitle>

  <Step number={1}>
    <StepTitle>Imperative Approach (State Mutation)</StepTitle>

    ```c
    int squaredSum(int* arr, int n) {
        int sum = 0;                       // Mutable state
        for (int i = 0; i < n; i++) {      // Explicit loop control
            sum += arr[i] * arr[i];        // State mutation
        }
        return sum;
    }
    ```
  </Step>

  <Step number={2}>
    <StepTitle>Functional Approach (Pure Composition)</StepTitle>

    ```haskell
    squaredSum :: [Int] -> Int
    squaredSum = sum . map (\x -> x * x)
    ```
  </Step>

  <Step number={3}>
    <StepTitle>Analysis</StepTitle>

    The imperative version relies on mutable variables and explicit control flow. The functional version is a pure composition of mathematical transformations with no hidden state.
  </Step>
</StepByStep>

<HighlightCard
  variant="neutral"
  title="Definition 1.2.3: The Von Neumann Bottleneck"
  description="The performance limitation inherent in imperative programming due to hardware architecture."
>

Imperative programming directly mirrors the Von Neumann architecture, where the CPU and memory are separated by a shared bus. Computation requires repeatedly shuttling data across this bus (FETCH, ALU, STORE). John Backus identified this as the "Von Neumann bottleneck," as the algorithm is buried in memory-management noise rather than mathematical logic.

</HighlightCard>

<HighlightCard
  variant="neutral"
  title="Definition 1.2.4: Referential Transparency"
  description="The property that allows expressions to be replaced by their values without changing program behavior."
>

An expression is **Referentially Transparent** if it can be replaced by its corresponding value without changing the program's behaviour. This is guaranteed *only* by pure functions.

**Consequence:** Referential transparency enables aggressive compiler optimisations, such as Common Subexpression Elimination (CSE), automatic memoisation, and safe inlining.

</HighlightCard>

<Card>

### Definition 1.2.5 (Compiler Optimisations via Purity)

Because pure functions guarantee referential transparency, the GHC compiler can safely apply:
1. **Common Subexpression Elimination (CSE):** Evaluating `f x` once and sharing the result if it appears multiple times.
2. **Inlining:** Replacing function calls with the function body, knowing it cannot alter observable side effects.
3. **Memoisation:** The runtime automatically shares the results of lazy thunk evaluations.

</Card>
