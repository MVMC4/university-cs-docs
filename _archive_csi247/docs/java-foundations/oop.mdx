# Object-Oriented Programming (OOP)

Object-Oriented Programming (OOP) is a structural paradigm designed to manage software complexity by modeling real-world entities as interacting objects.

---

## 1. User-Defined Classes & Objects

Java is Object-Oriented. **Classes** are blueprints; **Objects** are instances.

### Anatomy of a Class

```java
public class Car {
    // 1. Fields (State)
    private String model;
    private int year;

    // 2. Constructor (Initialization)
    public Car(String model, int year) {
        this.model = model;  // 'this' = current object
        this.year = year;
    }

    // 3. Methods (Behavior)
    public void drive() {
        System.out.println("The " + model + " is driving.");
    }

    // 4. Getters/Setters (Encapsulation)
    public String getModel() { return model; }
    public void setModel(String model) { this.model = model; }
}
```

### Instantiation

```java
Car myCar = new Car("Toyota", 2022);
myCar.drive(); // "The Toyota is driving."
```

## 2. The Four Pillars of OOP: Architectural Mechanics

### 1. Encapsulation: State Protection and Interface Contracts

Encapsulation is the bundling of data (state) and methods (behavior) into a single unit while restricting direct access to internal components. Its primary architectural objective is to enforce class invariants and prevent external state corruption.

#### Access Modifiers and Visibility
Java enforces encapsulation through a four-tier visibility model.

| Modifier | Class | Package | Subclass | Global | Architectural Use Case |
| :--- | :---: | :---: | :---: | :---: | :--- |
| `private` | Yes | No | No | No | Internal state, sensitive data. |
| *default* | Yes | Yes | No | No | Package-private utilities. |
| `protected` | Yes | Yes | Yes | No | Methods intended for overriding. |
| `public` | Yes | Yes | Yes | Yes | The public API contract. |

#### Accessors, Mutators, and Invariant Enforcement
Accessors (getters) and mutators (setters) are validation gates. By routing all state mutations through mutators, a class can enforce invariants.

```java
public class BankAccount {
    private double balance;

    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Deposit must be positive.");
        }
        this.balance += amount;
    }
}
```

<Callout type="warn" title="The Hazard of Public State:">
If a class exposes public mutable fields (e.g., `public double balance`), any external module can corrupt the state. Encapsulation forces all state transitions through controlled methods.
</Callout>

#### Class-Level State: The `static` Keyword
- **Static Variables**: Shared across all instances in the JVM Method Area.
- **Static Methods**: Utility functions that operate without instance context (e.g., `Math.max()`). They cannot access instance variables or utilize the `this` reference.

### 2. Inheritance: Hierarchical Classification and Coupling

Inheritance establishes an "IS-A" relationship, allowing a subclass to inherit the state and behavior of a superclass.

#### Constructor Chaining and `super`
When a subclass is instantiated, Java must initialize the superclass state first via `super()`.

```java
public class Vehicle {
    protected String make;
    public Vehicle(String make) { this.make = make; }
}

public class Car extends Vehicle {
    private int numDoors;
    public Car(String make, int numDoors) {
        super(make); // CRITICAL: Must be the first line!
        this.numDoors = numDoors;
    }
}
```

<Callout type="info" title="Architectural Trade-off: Composition over Inheritance">
Inheritance creates a "Fragile Base Class" problem. Use inheritance strictly when a true "IS-A" relationship exists. If the goal is merely code reuse, use **Composition** to maintain loose coupling.
</Callout>

### 3. Polymorphism: Dynamic Method Dispatch

Polymorphism allows objects of different concrete classes to be treated as objects of a common superclass. The exact method execution is determined at runtime via **Dynamic Method Dispatch** (vtable).

#### Compile-Time vs. Run-Time Polymorphism
1.  **Method Overloading (Compile-Time)**: Same name, different parameter signatures.
2.  **Method Overriding (Run-Time)**: Subclass provides a specific implementation of a superclass method.

```java
// Upcasting: Treating a specific type as a general type
List<PaymentMethod> checkoutCart = new ArrayList<>();
checkoutCart.add(new CreditCard());
checkoutCart.add(new CryptoWallet());

// Dynamic dispatch: The JVM invokes the correct overridden method at runtime
for (PaymentMethod pm : checkoutCart) {
    pm.pay(100.0);
}
```

---

### 4. Abstraction: Hiding Implementation Complexity

Abstraction separates the logical properties of an object (the "what") from its implementation details (the "how").

#### Abstract Classes vs. Interfaces

| Feature | Abstract Class | Interface |
| :--- | :--- | :--- |
| **Relationship** | IS-A (Core identity) | CAN-DO / ACTS-AS (Behavioral capability) |
| **State** | Can maintain instance variables | No instance state (only constants) |
| **Constructors** | Yes (invoked by subclasses) | No |
| **Inheritance** | Single inheritance only | Multiple implementation |

#### Design Principle: Program to an Interface
```java
// Rigid: Tied to a specific implementation
ArrayList<String> list = new ArrayList<>();

// Flexible: Tied to an abstraction
List<String> list = new ArrayList<>();
```

## Summary

- **Classes/Objects**: Blueprints and instances.
- **Encapsulation**: State protection via access modifiers.
- **Inheritance**: Hierarchical classification via `extends`.
- **Polymorphism**: Dynamic method dispatch via overriding.
- **Abstraction**: Hiding complexity via interfaces and abstract classes.
